## 1. Objective and developer decisions

Implement **all justified performance corrections as one coordinated batch**, including the outdated-test corrections needed for a trustworthy final check. Optimize primarily for **lower-end Android phones**, but **do not request Android profiling, ADB/Perfetto, manual benchmark setup, or prepared-save playthroughs from the developer**. Use the audit's actual desktop measurements, source-level evidence and sensible mobile constraints. Avoid fabricated performance guarantees: a desktop improvement is not an Android benchmark.

**Testing cadence explicitly approved for this batch:** Finish implementing the entire batch before running the heavy validation. **Do not rerun the whole suite after individual fixes**, and **do not conduct multiple rounds of benchmark scenarios while coding**. Use existing audit measurements as the baseline, then do **one coordinated end-of-batch verification phase**: static/import checks as appropriate, the maintained full regression suite **once**, and the deterministic desktop performance benchmark **once**. If the final run exposes a fault, correct the fault, use the narrowest relevant check to confirm it, and repeat the full suite only if that fix could invalidate previously passing coverage. Run heavy tests sequentially. This is a deliberate economical exception to the Playbook's usual earlier targeted-probe cadence (§§44.2, 60.1).

**Development saves:** Apply Playbook §61.1 literally. Older development profiles **do not require compatibility, conversion, refunds, or migrations**. If an optimized representation needs a fresh schema or a reset, make it and say so. Do not spend tokens adding old-save compatibility cases. Still keep the **current-version** save/load path usable, valid, and capable of a straightforward disk round trip. Do not intentionally introduce a save system that routinely writes broken files. Preserve essential atomic replacement/backup behavior unless there is a measured, simpler equally safe design. A source change affecting persistence must correctly handle the present schema, default initialization, resets, and Prestige ownership.

**Design preservation:** Keep accepted Stage 1–5 balance unchanged. Do not modify the mechanics, rewards, spawn rules, fog visibility, combat decisions, weather look, pixel-art filtering, skills, UI layout/feel or graphical assets merely to make numbers faster. Prefer event-driven updates, caching, compact data and off-screen *presentation* culling. The simulation must stay authoritative; off-screen enemies must continue gameplay correctly. Retain editor-editable scenes/resources where already available. No broad architectural rewrite or speculative new feature.

**Commit autonomously:** Once the entire batch is implemented and final checks are recorded, **make the Git commit yourself**. Do not ask the developer to commit. Follow the repository's current sequential `Change N: ...` history; inspect `git log` first and use the next number. In the audited baseline the latest commit is `Change 23`, so this batch is **Change 24** unless the live repository has since advanced. Per Playbook §44.3, align the new `project.godot` game change version and Android version code with **Change 24** (or the actual next integer); leave Android `version/name` blank when inherited. This resolves the earlier mismatch (Change 23 commit, app/code 22). Android version codes need only be monotonic, not gap-free. Do not change the save schema merely to track the game version. Stage only batch-owned code/docs/tests and authorized audit documentation, not unrelated developer changes or secrets. No push or publishing unless a separate instruction expressly requires it.

## 2. Required performance corrections (one batch)

These are **audit-derived opportunities**, not promises that every candidate optimization is beneficial. Implement them together where technically justified; inspect the real project before choosing the safest mechanism. If an item is unsuitable or has no measurable benefit, explicitly document why rather than adding risky complexity.

| ID | Audit finding / baseline | Required action and boundaries |
|---|---|---|
| P01 — Save path | PERF-01: fully explored late-game save ~466 KB, ~125 ms per save on desktop; ~5 s cadence | Remove unnecessary full JSON re-parsing of newly written temporary and old primary save data where equivalent verification can be cheaper. Avoid duplicate serialization/parsing and repeated whole-state copies. Keep an actual valid current-schema JSON disk round trip and sensible recovery on write failure. |
| P02 — Fog save representation | PERF-01: 30,864 string-keyed explored-cell entries in full exploration | Prefer a compact bitset, packed array, or other deterministic per-stage representation for persistent explored cells **if** it materially reduces save cost and map-memory churn. Update all affected current-schema reads/writes, reveal, UI and Prestige behavior consistently. Development reset/schema bump is allowed; no legacy migration. |
| P03 — Autosave scheduling | PERF-01: marked dirty every ~2 s; flushed ~5 s | Coalesce repeated dirty marks and avoid frequent whole-profile writes from routine farming. Keep prompt saves for significant committed state changes and app background/exit; explicitly document the new ordinary-progress rollback window. Don't silently lose important committed actions. |
| P04 — World transitions | PERF-02: 300–420 ms blocking stage switches | Remove synchronous scene `load()` + instantiate work from a critical frame where practical. Use verified `ResourceLoader.load_threaded_request` or preloading/caching with a short non-blocking transition and limited cache memory. Respect travel locks, enemy/camp state, cancellation, and invalid destinations. Do not make progress or stage selection inconsistent. |
| P05 — Inventory UI | PERF-04: ~8.4 ms refresh with unchanged contents; ~25 ms forced | Stop re-applying layout/theme/font/size changes to 70+ slots on every kill or unrelated `sim.revision`. Use inventory-specific change signatures/dirty flags and re-layout only on real slot-count, density, size, or viewport changes. Preserve all slot interactions and scroll behavior. |
| P06 — Actor views/simulation | PERF-03: all actors updated each frame; repeated lookups and allocations | Cache immutable group/item definitions and attack textures; load assets once, not per actor per frame. Cull or throttle off-screen **visual** work while keeping simulation/spawns/attacks/timers correct. Eliminate unnecessary duplicated enemy arrays and repeated temporary allocations in simulation hot paths without changing action order or determinism. |
| P07 — Fog/map/rain | PERF-03: String-key formatting per cell/particle and repeated full fog/minimap redraw | Cache visibility and explored-cell lookups in efficient representations; redraw based on actual discovery/viewport changes. Reduce expensive rain particle checks and fog/minimap rebuilds, particularly Summer II and Spring II, **without changing visible fog disclosure, splash behavior, weather density, or look**. |
| P08 — Panel spikes | PERF-05: Spring II repeated panels max 74 ms; Prestige panel spikes | Remove needless repeated panel construction, costly relayouts and redundant style writes on open/close. Prefer existing reconciler and cache where useful; avoid unbounded retained nodes. Preserve dialog settle/flicker fix and dynamic panel content. |
| P09 — Startup/memory | PERF-06: desktop scene load ~1.09 s; first frames ~564 ms; memory rises visiting maps | Audit excessive eager loads, unused retained stage/view resources, and repeat allocations. Make modest startup/memory corrections only when clearly safe. Do not replace boot architecture solely on speculation. Track stage-cache memory cost if adding caching. |
| P10 — Audio asset candidate | PERF-07: 23 MB source WAV background music, compressed on import | **Evaluate rather than automatically convert.** If imported runtime size/playback is already efficient, leave the audio unchanged; do not add a lossy conversion or licensing work solely to shrink the source repository. If a beneficial format change is clear, preserve looping, quality and volume behavior and document the change. |

### Key measurement anchors from the audit (desktop; not phone)

- Winter I idle: mean **3.10 ms**, p95 **4.42 ms**.
- Summer II rainy farming: mean **10.52 ms**, p95 **14.57 ms**.
- Spring II rainy farming, 135 actors: mean **14.15 ms**, p95 **22.21 ms**, p99 **27.20 ms**.
- Spring II walking into unexplored fog: mean **15.74 ms**, p99 **31.93 ms**.
- Stage switches: **300–420 ms** individual stalls, benchmark max **422.03 ms**.
- Late-game save: median **125.0 ms** for 465,980-byte profile.
- Inventory: **8.4 ms** unchanged refresh, **25.2 ms** forced full layout.

The audit used Godot 4.7.2, Windows 10, Intel i5-10300H, GTX 1650, 540×960 Compatibility viewport, V-Sync off, a separate no-autosave test profile. Its original performance harness was a scratch script, not necessarily checked in. Rebuild a small **non-gating, deterministic desktop benchmark** using the Playbook §48.1 method and scenario builders (not a manually maintained fixed save); match the scenario/environment where possible. If the new harness differs, **flag comparisons as approximate**, not scientifically matched. Run its end-of-batch scenario pass **once**. Print mean, p50/p95/p99/max frame intervals, save time/size, stage-switch stalls, inventory layout timings, node/object counts, Godot build, renderer and machine. Never assert phone FPS or declare low-end performance guaranteed.

## 4. Implementation boundaries and risk controls

- Do **not** rebalance stages, enemies, upgrades, missions, Prestige rewards or skill values. Stage 1–5 balance is developer-accepted; Stages 6–8 remain unaccepted. Do not unlock or implement new gameplay, the demo, localization, marketing, store assets, or publishing.
- Do **not** perform a full UI redesign, asset export cleanup, ARM ABI adjustment, Android back gesture work, or release/legal tasks here. Those have separate future Claude chats, unless a minimal adjustment is strictly necessary to make the performance batch function.
- Do **not** change the user-visible look of rain, fog, sprite filtering, weapon/skill VFX, boss positions, or button/slot layout. Performance wins must not silently degrade the game.
- Do **not** run or require Android profilers, ADB traces, prepared manual late-game saves or extensive developer walkthroughs. No release export is required by this batch; the next device UI/UX chat will handle final Android inspection.
- Do **not** spend effort on migrations, obsolete development-save compatibility, old-schema fault-injection matrices, or rescuing pre-release progress. Follow Playbook §61.1; if the old profile resets, report it clearly. **Current-schema** saving/loading, basic backup/recovery and newly added field lifecycle must still function.
- Do not leave benchmark instrumentation, debug overlays or performance shortcuts enabled in production gameplay or exported release builds.
- Only optimize with a causal explanation; mark hypotheses as such, and don't claim desktop values prove Android performance.
- Preserve the developer's worktree, isolated profiles, Git history, existing GDD authority, and editor editability. Never commit signing credentials, developer private files, unneeded artifacts, or unrelated changes.

## 5. Final validation — run after the whole batch is implemented

**Run the expensive validation at the end, not separately after each optimization.** Record actual commands and counts.

1. **Source/import health:** Confirm Godot loads the project and relevant scenes; run static/check-only tools as required. Fix script errors and invalid references without modifying unrelated gameplay.
2. **Full maintained suite:** Run `python tools/run_probes.py` **once** on isolated profiles, sequentially. With the registered Change 22 probe the baseline suite should have **31 entries** (previously 30); count the actual live runner and report it honestly. Any `SCRIPT ERROR`, timeout, missing summary or assertion failure is a failure. The target is **all passing**, including full Guided flow; if failures arise, correct and use narrow reruns, rerunning the full suite only as needed for integrity.
3. **Non-gating desktop benchmark:** Run **one** end-of-batch set of the documented scenarios using current code and the real main scene (Winter I quiet; Summer II rainy; Spring II rainy at maximum spawned actors/full 70 slots/automation; Spring II exploration; repeated panels and Prestige; repeated stage switches; late-game save and inventory microbenchmarks). Use saved fixture builders isolated from production saves. Report actual results and compare to audit's baseline **only where environments and fixtures are comparable**.
4. **Current-schema minimal save check:** Verify current-version serialize→disk→load and fresh-profile writable state (including exploration, inventory, Prestige ownership as relevant). This is correctness, **not old-save migration testing**. A schema change may reset old development saves.
5. **No uncontrolled regressions:** Verify equivalent gameplay decisions, fog disclosure, weather visual behavior, tutorial availability/waits, panel control semantics, audio and inventory controls with existing automated coverage plus minimal rendered desktop inspection where useful. Do not run long late-game pacing bots or unrelated marketing pipelines for this performance batch.
6. **Git hygiene:** Check repository diff and status, document benchmark/test output paths, ensure generated files do not dirty committed historical evidence, and then commit the complete validated batch autonomously. If blocked by an actual test or environment fault, disclose it; do not fake a pass or hide the problem merely to commit.
